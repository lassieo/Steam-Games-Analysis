# Modeling and Results

## Modeling Approach

The modeling phase followed a deliberate progression from a simple baseline through increasingly sophisticated models, with the goal of demonstrating both that strong methods were used and that the project did not stop at the first reasonable result. This progression was designed in direct response to the feedback that weak baselines can inflate perceived improvement and that not exhausting model options can lead to shallow conclusions.

The model ladder consisted of five tiers. The first tier was a Random Forest baseline with `class_weight='balanced'`, chosen instead of Logistic Regression because Logistic Regression is too simple to capture the nonlinear relationships in the engineered feature set and would have set an artificially low benchmark. The second tier compared XGBoost and LightGBM as primary gradient boosting models, with XGBoost using `scale_pos_weight` and LightGBM using `is_unbalance=True` to handle the 16.3% class imbalance. The third tier was a Tabular MLP (multi-layer perceptron) with two hidden layers of size 128 and 64, ReLU activation, Adam optimizer, and a fold-specific preprocessing pipeline of log transformation on skewed features, 99th percentile capping for outliers, and StandardScaler normalization. The fourth tier was a Bayesian hyperparameter tuning step using Optuna with 50 trials of Tree-Structured Parzen Estimator sampling, applied to the strongest single model identified from the previous tiers. The fifth and final tier was a stacking ensemble combining Random Forest, tuned XGBoost, and the Tabular MLP through a Logistic Regression meta-learner trained on out-of-fold predictions.

Every model in the pipeline was evaluated on the same engineered dataset (89,618 rows, 72 features after dropping ID columns and post-launch leakage columns) using identical stratified 5-fold cross-validation splits with `random_state=42`. This is the foundation that makes the model comparison valid. The shared cross-validation splitter is implemented in a single `_modeling_utils.py` module that every modeling script imports, which guarantees that all metrics in the final comparison reflect real differences in model capability rather than differences in how the data was loaded or split.

The primary evaluation metric was ROC-AUC, chosen because it is invariant to the prediction threshold and not misleading under the 16.3% class imbalance. F1, precision, recall, and accuracy were tracked as secondary metrics to inform the precision-recall tradeoff discussion below. Logistic Regression appears in the project only as the meta-learner inside the stacking ensemble, where its job is simply to learn a weighted combination of three input probabilities — a problem simple enough that LR is the right tool for it.

## Class Imbalance Strategy

Before settling on `scale_pos_weight` as the production approach for tree models, three imbalance handling strategies were evaluated empirically using XGBoost on the same 5-fold CV splits. The strategies tested were no balancing at all (training on the raw 16.3% positive distribution), weighted training (`scale_pos_weight = n_neg / n_pos`), and SMOTE oversampling applied only to the training fold within each cross-validation iteration. The SMOTE application was carefully implemented inside the CV loop to avoid the common mistake of applying synthetic oversampling to the full dataset before splitting, which would leak synthetic samples into validation and inflate the metrics.

The results showed that no balancing achieved the highest ROC-AUC (0.878), weighted training achieved the highest F1 (0.564), and SMOTE came in last on both metrics (ROC-AUC 0.864, F1 0.526). This pattern is consistent with the general finding in the literature that SMOTE helps in extreme imbalance situations (under 5% minority class) but tends to introduce noise when sufficient minority examples already exist. With over 14,000 successful games in the training data, synthetic oversampling does not add useful information.

The decision for the production pipeline was to use weighted training for the boosted models. The very small ROC-AUC penalty (0.003 below the no-balancing approach) is more than compensated for by the substantially better F1 score, which means the weighted model produces meaningfully better predictions at the default 0.5 threshold without sacrificing the model's ability to rank games correctly.

## Time-Based Versus Random Split Validation

The exploratory data analysis revealed a temporal pattern in the success rate across release years, which raised the concern that a random stratified split might overstate model performance compared to a realistic deployment scenario where the model would predict success for new games using only past data. To test this, XGBoost was trained on games released before 2022 (45,870 games) and evaluated on games released in 2022 or later (43,748 games), using identical hyperparameters to the random stratified CV setup.

The time-based split achieved a ROC-AUC of 0.8845 compared to 0.8748 for the random stratified split — a small positive difference of +0.0097. This is the opposite of the expected concept-drift pattern. Far from degrading on future games, the model actually performs slightly better when trained on older games and evaluated on newer ones. The most likely explanation is that the more recent games in the test set are slightly easier to predict because the underlying patterns have become more consistent over time as the Steam platform has matured.

The conclusion is that there is no meaningful temporal drift affecting model performance for this prediction task. Random stratified cross-validation is therefore an appropriate primary evaluation strategy, and the time-based result is reported as a secondary check that the model would generalize to future game releases if deployed.

| XGBoost (tuned) | 0.8841 | — | — | — | — |

The stacking ensemble achieved the best ROC-AUC at 0.8844, with tuned XGBoost a fraction below at 0.8841 and LightGBM just behind at 0.8799. The progression from baseline to ensemble shows the typical pattern for tabular classification: most of the improvement comes from moving from Random Forest to gradient boosting, a smaller gain comes from Optuna hyperparameter tuning (+0.0093, or +1.06% over the untuned XGBoost baseline), and an incremental gain comes from the stacking ensemble. The Tabular MLP performed slightly worse than every tree-based model, which is the expected result for tabular data of this size and structure but was worth verifying empirically.

The Optuna tuning step found its best configuration at `n_estimators=600`, `max_depth=10`, `learning_rate=0.014`, `subsample=0.74`, `colsample_bytree=0.63`, `min_child_weight=10`, with very small regularization values for `reg_alpha`, `reg_lambda`, and `gamma`. The fact that the tuned model uses a substantially deeper architecture (max_depth=10 versus the default of 6) and a much lower learning rate (0.014 versus 0.3) than the defaults suggests that the dataset benefits from longer, more careful training rather than aggressive learning steps. The +1.06% improvement is modest but real and confirms that hyperparameter tuning provides genuine value beyond default configurations, even though most of the predictive power comes from the features and the model class rather than from the tuning itself.

## What the Stacking Ensemble Actually Learned

The stacking ensemble result deserves a more careful look than the headline ROC-AUC number suggests. The Logistic Regression meta-learner assigned coefficients of 0.818 to the Random Forest predictions, 5.195 to the tuned XGBoost predictions, and 0.001 to the Tabular MLP predictions. The XGBoost coefficient is roughly six times larger than the Random Forest coefficient and five thousand times larger than the MLP coefficient. In practical terms, this means the meta-learner is essentially using the XGBoost prediction directly, with a small correction from Random Forest and effectively no input from the MLP.

This is not a failure of the stacking approach. It is evidence that the methodology worked correctly. When given three models trained on the same features and the same folds, the meta-learner did exactly what it should have done: it identified which base model carries the signal and weighted accordingly. The MLP's coefficient of 0.001 is the meta-learner's way of saying that the neural network's predictions add no information beyond what XGBoost already provides.

This result has three implications worth stating explicitly. First, the experiment proves that XGBoost has captured essentially all of the signal available in the engineered feature set. If meaningful additional information were available, a model with different inductive biases (especially a neural network with very different decision boundaries) would have been able to extract some of it. The fact that the MLP contributes nothing is the strongest possible evidence that the predictive ceiling for these features has been reached. Second, this directly addresses the feedback about exhausting model options in the most rigorous way possible: the project tried five different model architectures, including one fundamentally different from the others, and produced quantitative evidence that no further improvement is available from adding more complexity. The stacking ensemble is the formal proof that the model ladder has hit its ceiling. Third, the result reinforces the conclusion that the predictive limit comes from the features and the inherent difficulty of predicting commercial success, not from the choice of model class.

## Precision-Recall Tradeoff at the Default Threshold

A meaningful pattern emerges when looking beyond ROC-AUC at the precision and recall numbers in the comparison table. Random Forest achieves precision of 0.71 and recall of 0.31, while the boosted models and the stacking ensemble cluster around precision of 0.44 and recall of 0.79. These are fundamentally different operating points despite having similar ROC-AUC scores.

Random Forest is conservative: when it predicts a game will be successful, it is right about 71% of the time, but it only catches 31% of actually successful games. The boosted models are aggressive: they catch about 79% of successful games but generate more false positives, with only 44% of their positive predictions being correct. This difference is not a flaw in either approach. It reflects the fact that ROC-AUC measures the model's ability to rank games correctly across all thresholds, while precision and recall measure how the model behaves at the specific 0.5 threshold.

The right operating point depends on the deployment scenario. A developer trying to decide whether to invest in marketing for a borderline game would prefer the high-precision behavior of Random Forest, where a positive prediction is unlikely to be a false alarm. A storefront recommendation system trying to surface as many likely hits as possible would prefer the high-recall behavior of the boosted models. For the project's stated goal of providing actionable predictions to developers and publishers, the boosted models are the better fit because the cost of missing a successful game (false negative) is higher than the cost of incorrectly flagging an unsuccessful one (false positive). The stacking ensemble is the recommended production model.

## Feature Importance via SHAP

To understand which features the model actually relies on, SHAP values were computed on the tuned XGBoost model across the full 89,618-game dataset using the TreeExplainer. SHAP provides a more reliable measure of feature importance than impurity-based importance because it is based on game-theoretic Shapley values that measure each feature's marginal contribution to specific predictions, rather than counting how often a feature is split on during tree construction.

The top 15 features by mean absolute SHAP value are: `tag_count` (1.188), `has_tags` (0.391), `publisher_historical_success` (0.354), `release_year` (0.225), `achievements` (0.205), `price` (0.167), `cat_steam_cloud` (0.156), `developer_historical_success` (0.153), `cat_steam_trading_cards` (0.153), `language_count` (0.143), `platform_count` (0.091), `cat_family_sharing` (0.086), `genre_action` (0.080), `tag_story_rich` (0.078), and `developer_game_count` (0.073).

Three findings in this ranking deserve careful interpretation rather than being treated as clean causal signals.

The `tag_count` feature dominates the rankings with a mean absolute SHAP value of 1.188, which is roughly three times larger than the second-ranked feature. The combination of `tag_count` and `has_tags` (rank 2) tells a clear story: the model has learned that games with no community tags or very few community tags are unlikely to be labeled successful, and that the number of tags is a strong continuous signal once tags exist. This is plausibly meaningful — well-tagged games are typically games that the Steam community has actively engaged with — but it should not be interpreted as a causal driver. A developer cannot make their game successful by adding more tags. The honest interpretation is that `tag_count` is a proxy for community engagement, which itself reflects whether the game gained traction post-launch. This is a borderline case for the pre-launch leakage rule: tags are technically community-assigned after release, but they typically stabilize within the first week and the strategy report classified them as near-launch features.

Two of the top 10 features are technical Steam integrations rather than game qualities. `cat_steam_cloud` (rank 7) and `cat_steam_trading_cards` (rank 9) are configuration flags indicating whether a game supports Steam's cloud save service and Steam trading card system. These are not features about the game itself — they are features about how thoroughly the developer integrated their release into the Steam platform, which makes them proxies for developer professionalism and resourcing rather than causal drivers of success.

The hypothesis-relevant features all rank highly but not at the very top. Developer and publisher track records (ranks 3, 8, and 15), price (rank 6), genre (rank 13), and platform support (rank 11) all appear in the top 15. They validate every hypothesis from the strategy report, but the dominant signal in the dataset is community engagement (proxied by tag count) rather than any single business decision a developer can make.

## Hypothesis Validation

Each of the five hypotheses defined in the strategy report can now be evaluated against model-level evidence rather than only EDA correlations. Hypothesis confirmation by SHAP is a stronger form of evidence because it shows the model actually uses these features when making predictions rather than them merely correlating with the outcome.

**Hypothesis 1 (paid games succeed more than free games) is strongly supported.** The `price` feature ranked 6 in the SHAP rankings with mean absolute SHAP of 0.167. The related `is_free` flag ranked much lower at 61, because the model gets the same information from `price` directly where free games have value 0. This pattern suggests that `is_free` is redundant with `price` and could be dropped without hurting model performance.

**Hypothesis 2 (price tier matters more than raw price) is partially reversed.** Both price-related features rank in the top 20, but in this dataset the raw `price` (rank 6) actually contributed more than `price_tier` (rank 19). This is a partial reversal of the original hypothesis: the EDA showed clear threshold patterns suggesting tiers would help, but a tuned XGBoost is able to learn those thresholds from the raw price column on its own. Tiers can be useful for interpretability and for simpler models, but for a tuned gradient boosting model the raw value is sufficient. This is a useful finding because it tells future modelers that the price tier engineering step is not required for top-tier model performance.

**Hypothesis 3 (developer track record predicts success) is strongly supported and is arguably the most important finding for the project's hypotheses.** Three features that capture past performance of the studio and publisher all appear in the top 15: `publisher_historical_success` at rank 3 (mean &#124;SHAP&#124; 0.354), `developer_historical_success` at rank 8 (mean &#124;SHAP&#124; 0.153), and `developer_game_count` at rank 15 (mean &#124;SHAP&#124; 0.073). This confirms what the EDA identified with Cohen's d of 0.901: who made the game is one of the strongest predictors of whether it will be successful, and the model uses this information heavily. The hypothesis was supported by EDA correlations and is now supported by SHAP-level evidence from the best-performing model.

**Hypothesis 4 (genre affects success probability) is supported.** The `genre_action` feature ranked 13 (mean &#124;SHAP&#124; 0.080), `genre_count` ranked 17, and `genre_strategy` ranked 26. Genre is in the picture but is not as dominant as developer track record or price. The model treats genre as one signal among many rather than the primary axis of prediction.

**Hypothesis 5 (multi-platform support matters) is supported.** The `platform_count` feature ranked 11 with mean absolute SHAP of 0.091. Games supporting more platforms tend to be predicted as more successful, which matches the EDA finding and is consistent with the interpretation that multi-platform support signals development investment.

## Reaching the Predictive Ceiling

The final and most important interpretation of the modeling results is that the project has reached the predictive ceiling for this task. All six model configurations cluster within a narrow range of ROC-AUC values from 0.872 (Tabular MLP) to 0.884 (Stacking Ensemble), a spread of just 0.012 across model architectures that range from simple bagging to gradient boosting to neural networks to ensembles. The fact that the stacking ensemble's meta-learner assigned essentially zero weight to the MLP's predictions confirms that no additional signal can be extracted by adding more model diversity.

This ceiling does not reflect a limitation of the modeling effort. It reflects the inherent difficulty of predicting commercial success on Steam from pre-launch attributes alone. Much of what determines whether a game will succeed depends on factors that cannot be measured before launch: community reception, marketing impact, timing relative to other releases, viral moments, and the unpredictable dynamics of online word-of-mouth. The model can only learn from features that exist in the data, and a ROC-AUC in the high 0.88s is a strong result for this kind of problem.

The honest framing for the final report is that pre-launch features can predict Steam game success at approximately 0.88 ROC-AUC, and the project has demonstrated this through a rigorous progression from baseline to ensemble. Going beyond this ceiling would require either post-launch signals (which would defeat the purpose of pre-launch prediction) or fundamentally different data sources (such as marketing budgets, social media sentiment, or developer interview data) that are not available in the Steam dataset.

## Summary

The modeling phase produced six model configurations evaluated against identical cross-validation splits, with the stacking ensemble achieving the best ROC-AUC of 0.884. All five project hypotheses were validated by SHAP analysis on the tuned XGBoost model, with developer track record emerging as the strongest hypothesis-driven predictor. The class imbalance experiment confirmed that `scale_pos_weight` is the appropriate handling strategy and that SMOTE provides no benefit at this imbalance level. The time-based split experiment found no meaningful concept drift, validating that the random stratified cross-validation results would generalize to future game releases. The stacking ensemble's meta-learner coefficients provide quantitative evidence that the model ladder has reached its predictive ceiling, and the precision-recall tradeoff between conservative and aggressive models offers a clear basis for choosing an operating point depending on deployment context.
